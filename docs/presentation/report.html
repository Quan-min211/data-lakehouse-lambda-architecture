Phần 3

Kiến trúc tổng thể Lambda Lakehouse

Phân tách luồng dữ liệu 2 nhánh: Speed Layer (độ trễ micro-batch 5s) và Batch Layer (chính xác tuyệt đối, chu kỳ 15 phút), đồng bộ qua System Watermark.

📡 1. Data Sources
  • Binance REST API (15K bản ghi thực)
  • Mock GBM Generator (1.5M records)
  • Fault Injector (4 loại lỗi phân tán)
🔌 2. Ingestion Layer
  • ResilientKafkaProducer (acks=all, backoff)
  • Topic: crypto_trades_raw
  • Dead Letter Queue: crypto_trades_dlq
▼  Phân nhánh xử lý song song (Lambda Architecture)  ▼
🏭 3A. Batch Layer (Chu kỳ 15 phút)
  • MinIO (S3) + Apache Iceberg v2 Bronze
  • Dagster 6 SDA (DQ Gate, Dedup, Gold Agg)
  • Compaction Job: Bin-Pack 128MB / Expire
  • → Ghi ClickHouse: lakehouse.batch_agg
⚡ 3B. Speed Layer (Micro-batch 5s)
  • Spark Structured Streaming Trigger 5s
  • Watermark 1m, Tumbling Window 1m
  • Tính OHLCV, VWAP, Price Spike (≥2%)
  • → Ghi ClickHouse: lakehouse.speed_agg
🕐 lakehouse.system_watermark: Mốc thời gian W = Batch Cutoff — Căn cứ phân chia dữ liệu Reconciled vs Provisional
🔀 4. Serving Layer (FastAPI 3-Case Merger)
  • CASE 1 (T ≤ W): 100% Batch (Chính xác)
  • CASE 2 (T ≥ W): 100% Speed (Thời gian thực)
  • CASE 3 (Hybrid): Ghép tại W, ZERO Double-Count
📊 5. Dashboard UI (Streamlit + Plotly)
  • Biểu đồ nến OHLCV + VWAP + Cảnh báo Spike
  • Badge Nến Reconciled vs Provisional
  • Bảng đối soát sai lệch Δ = |VWAP_s - VWAP_b|

Cơ chế ClickHouse ReplacingMergeTree

Thay vì sử dụng Redis như đề xuất sơ khai, Speed View được nạp trực tiếp vào ClickHouse bảng ReplacingMergeTree(updated_at):

  • Tự động Upsert: Bản ghi mới trong cùng 1 cửa sổ nến sẽ ghi đè bản ghi cũ dựa vào updated_at.
  • Thống nhất Engine: Cả Batch View và Speed View đều nằm trên ClickHouse, giúp Serving Layer truy vấn đồng nhất bằng SQL siêu tốc.
  • Đạt chuẩn SLA: Thời gian từ khi có giao dịch đến khi hiển thị < 5 giây.
CASE 1 Lịch sử

T_end ≤ W: Lấy 100% từ batch_agg. Dữ liệu đã qua DQ Gate, chính xác tuyệt đối, Δ = 0.0.

CASE 2 Thời gian thực

T_start ≥ W: Lấy 100% từ speed_agg. Phục vụ tức thời cho trading, chấp nhận gần đúng.

CASE 3 Hybrid Ghép Nguồn

T_start < W < T_end: Cắt tại W, nửa trước lấy Batch, nửa sau lấy Speed. ZERO Double-Counting.

1. Redis → ClickHouse

Lưu Speed View trên ClickHouse giúp giảm 1 service phụ thuộc, cho phép Serving Layer JOIN/UNION dữ liệu bằng SQL siêu tốc mà vẫn giữ độ trễ < 5s.

2. 3-Case Query Merger

Thuật toán chia mốc theo Watermark W giải quyết triệt để lỗi tính 2 lần (Double-Counting) và tự động gắn nhãn Reconciled / Provisional.

3. Dagster SDA Pipeline

Thay vì chạy Spark Batch Job rời rạc, Dagster Software-Defined Assets quản lý dòng chảy lineage trực quan từ Bronze đến Watermark.
