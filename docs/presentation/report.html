📐 Công thức Mock GBM (Geometric Brownian Motion)

Mô hình toán học chuẩn trong tài chính để mô phỏng biến động giá ngẫu nhiên có drift & volatility thực tế:

dS = μ·S·dt + σ·S·dW
→ Rời rạc hóa (Euler–Maruyama):
S(t+1) = S(t) · exp((μ − σ²/2)·dt + σ·√dt·Z)
μ = 0.0 (drift trung tính)  ·  σ = 0.02 (độ biến động 2%/phút)
dt = 1/525,600 (mỗi tick = 1 phút/năm)  ·  Z ~ N(0,1)
S₀ = Giá thực tế cuối cùng của từng coin từ Binance

Phần 2

Kiến trúc tổng thể Lambda Lakehouse

Phân tách luồng dữ liệu 2 nhánh: Speed Layer (độ trễ micro-batch 5s) và Batch Layer (chính xác tuyệt đối, chu kỳ 15 phút), đồng bộ qua System Watermark.

📡 1. Data Sources
  • Binance REST API (15K bản ghi thực)
  • Mock GBM Generator (1.5M records)
  • Fault Injector (4 loại lỗi phân tán)
🔌 2. Ingestion Layer
  • ResilientKafkaProducer (acks=all, backoff)
  • Topic: crypto_trades_raw
  • Dead Letter Queue: crypto_trades_dlq
▼  Phân nhánh xử lý song song (Lambda Architecture)  ▼
🏭 3A. Batch Layer (Chu kỳ 15 phút)
  • MinIO (S3) + Apache Iceberg v2 Bronze
  • Dagster 6 SDA (DQ Gate, Dedup, Gold Agg)
  • Compaction Job: Bin-Pack 128MB / Expire
  • → Ghi ClickHouse: lakehouse.batch_agg
⚡ 3B. Speed Layer (Micro-batch 5s)
  • Spark Structured Streaming Trigger 5s
  • Watermark 1m, Tumbling Window 1m
  • Tính OHLCV, VWAP, Price Spike (≥2%)
  • → Ghi ClickHouse: lakehouse.speed_agg
🕐 lakehouse.system_watermark: Mốc thời gian W = Batch Cutoff — Căn cứ phân chia dữ liệu Reconciled vs Provisional
🔀 4. Serving Layer (FastAPI 3-Case Merger)
  • CASE 1 (T ≤ W): 100% Batch (Chính xác)
  • CASE 2 (T ≥ W): 100% Speed (Thời gian thực)
  • CASE 3 (Hybrid): Ghép tại W, ZERO Double-Count
📊 5. Dashboard UI (Streamlit + Plotly)
  • Biểu đồ nến OHLCV + VWAP + Cảnh báo Spike
  • Badge Nến Reconciled vs Provisional
  • Bảng đối soát sai lệch Δ = |VWAP_s - VWAP_b|

🎯 Vai trò tầng Ingestion

Đây là cửa ngõ duy nhất nhận dữ liệu từ bên ngoài vào hệ thống. Mọi bản ghi phải qua tầng này trước khi vào Lambda Architecture — đảm bảo tính thống nhất & khả năng phục hồi.

⚙️ Cách xây dựng & điểm kỹ thuật
  • Key Partitioning: Partition Kafka theo symbol → đảm bảo thứ tự event-time trong mỗi coin, tránh race condition.
  • Dead Letter Queue: Bản ghi vi phạm JSON Schema tự động route sang topic crypto_trades_dlq. Pipeline không bị chặn.
  • Idempotent Producer: acks=all + enable.idempotence=true → không mất & không nhân đôi message tại tầng mạng.
  • Resilient Reconnect: WebSocket tự động kết nối lại tối đa 5 lần với backoff 2ˢ khi mất mạng.
🎯 Vai trò tầng Batch

CASE 1 Lịch sử (History)

T_end ≤ W → 100% từ batch_agg. Đã qua DQ Gate, chính xác tuyệt đối. Δ = 0.0 bảo đảm.

CASE 2 Thời gian thực

T_start ≥ W → 100% từ speed_agg. Dữ liệu gần đúng, phục vụ trading tức thì < 5 giây.

CASE 3 Hybrid Ghép Nguồn

T_start < W < T_end: Cắt tại W — nến trước W lấy Batch, nến sau W lấy Speed. ZERO Double-Counting.
